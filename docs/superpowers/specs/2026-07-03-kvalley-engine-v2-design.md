# King's Valley — движок v2 под Вектор-06Ц (дизайн)

**Дата:** 2026-07-03
**Статус:** утверждён к реализации (после ревью спеки)

## Цель

Нативный движок King's Valley для Вектор-06Ц, который:
1. **Пробивает потолок ~24 Гц** текущего v1 (цель — **50 Гц**, один игровой тик на видеокадр ≈59904 такта).
2. **Портируется под другую графику без потери производительности** (Специалист монохром, ПК-8000 тайл-режимы, ПК-8002 «Эльф» с аппаратными спрайтами, БК) — все машины на КР580ВМ80А (i8080), кроме БК (PDP-11, отдельная ветка).
3. **Влезает в 16КБ** постоянного следа (код + сжатые данные + уровни + графика) — как БК-порт.
4. Стартует с **4 цветов** (проверено быстрым на БК-0011); 8 цветов — возможное развитие позже.

## Обоснование подхода (вариант C-native)

Потолок v1 — это накладные расходы **дословной рекомпиляции** Z80→i8080 (эмуляция
регистров через память для exx/ex af, эмуляция флагов для adc/sbc, ix-макросы), а
НЕ стоимость игровой логики. Доказательство: БК-0010 (PDP-11, всего 16КБ ОЗУ)
гоняет KV резво в 4 цвета. Дословная рекомпиляция раздувает код в 2–3× (v1 ≈27КБ
только кода) — в 16КБ физически не влезает.

Решение: **C-native** — компактный нативный i8080-движок с нуля, использующий всю
нашу байт-в-байт RE-работу (физика, формат уровней, лабиринт, AI мумий, ноты,
спрайты, графика) как ДАННЫЕ и знание, но НЕ транслируя код. Это устраняет
Z80-жир (→ 50 Гц реальнее) и укладывается в 16КБ. Ровно так сделан БК-порт
(трансляция скелета + машинные процедуры, но компактно).

Отвергнутые варианты: (A) только рендер — не бьёт логический потолок;
(B) полная замена без опоры на RE — теряем проверенную физику; (C-recompile) —
27→16КБ (−40%) почти нереально, Z80-жир на горячих тиках остаётся.

## Архитектура: три слоя, тонкий шов «сцена»

```
Слой 1: ЯДРО ИГРЫ (машинно-независимое, общее для всех i8080)
  Компактный нативный i8080 по RE-данным: лабиринт, физика актёров, AI мумий,
  ножи/предметы, game flow. НЕ трогает железо. Читает абстрактный ввод, пишет СЦЕНУ.
                              │
             СЦЕНА (портируемый шов — простые структуры в ОЗУ)
                              │
Слой 3: ДРАЙВЕР МАШИНЫ (свой на каждую) — реализует render_frame нативно
  Вектор: 2-плоск. dirty-блит фона + XOR-спрайты two-pass + ВИ53-звук
  Специалист: моно-блит + бипер · ПК-8000: реж.1 быстрые тайлы · Эльф: HW-спрайты
```

Ключевое отличие от v1: там логика пишет в ЭМУЛИРОВАННУЮ MSX-видеопамять, а мы
декодируем каждую запись (WRTVRM: маскирование адреса, расчёт банка, теневая
запись, пометка dirty). В v2 логика пишет **сцену напрямую** — декодирования нет.
Это и главная экономия тактов, и чистый шов для портов.

### Слой 2 — интерфейс сцены (точный контракт)

Данные (простые структуры в ОЗУ):
```
tilemap[768]      ; 24×32, байт = id тайла фона (лабиринт + динамика: дыры/предметы)
dirty_list[]      ; клетки, изменённые с прошлого кадра (обычно единицы)
sprites[N]        ; актёры кадра: {y, x, frame, color, flags}, N≈16
                  ; (герой + ≤7 мумий + ножи + предмет-в-руке)
palette[4]        ; 4 цвета сцены
```

Точки входа (ядро → драйвер машины) — весь порт под новую машину сводится к ним:
```
set_tile(cell,id) ; ЕДИНСТВЕННОЕ место правки фона: tilemap[cell]=id + пометка dirty
render_frame()    ; раз в тик: dirty-фон + спрайты two-pass XOR + палитра + презент
load_gfx(level)   ; распаковка (ZX0) паттернов тайлов/спрайтов уровня
input_read()      ; абстрактный ввод (клава/джойстик) → стандартные биты кнопок
sound_*           ; звук (ВИ53 на Векторе/Эльфе; бипер на Специалисте/БК)
```

Поток за тик:
1. Ядро двигает актёров → перезаписывает `sprites[]`; события уровня → `set_tile()`.
2. Ядро зовёт `render_frame()` один раз.
3. Драйвер: блит dirty-тайлов фона (дёшево), two-pass XOR-спрайты (проверенный
   конвейер v1: erase-all→draw-all, мультиплекс-безопасно), палитра, презент.
   Драйвер держит свою копию «прошлого кадра» спрайтов — ядро об этом не знает.

## Раскладка памяти (целевой бюджет 16КБ)

16КБ = ПОСТОЯННЫЙ след (код + сжатые данные), как на БК. Распакованное/рабочее
живёт в машинном ОЗУ/видеопамяти (у Вектора: 0x8000-0xFFFF + свободные 0x4000-0x8000).

Постоянный след:

| Блок | ~Размер | Сжатие |
|---|---|---|
| Ядро игры (логика: лабиринт/физика/AI/потоки) | 4–5 КБ | нет (код) |
| Драйвер Вектора (рендер сцены + ВИ53-звук) | 2–3 КБ | нет (код) |
| Bootstrap + распаковщик ZX0/deexo | 0.5 КБ | нет |
| Тайлы фона (паттерны) | ~1 КБ | ZX0 |
| Спрайты актёров (паттерны) | ~1 КБ | ZX0 |
| Шрифт HUD/меню | ~0.5 КБ | ZX0 |
| Уровни (лабиринты пирамид) | 2–3 КБ | ZX0 (формат вскрыт) |
| **Итого** | **~13–16 КБ** | впритык, реально |

Рабочее ОЗУ (транзиентное, вне 16КБ-бюджета, машинно-специфичное): сцена
(tilemap 768Б + sprites + dirty), распакованные паттерны уровня, структуры
актёров, состояние звука, стек, scratch распаковки.

Следствия: уходят ~14КБ MSX-эмуляционных теней v1 (SAT/colour-таблицы) — в v2 их
нет, только сцена + паттерны. Куда класть распакованное — решает драйвер машины
(часть портируемого шва).

## Пошаговая миграция без регрессии (критический принцип)

Не big-bang. Замена модуль-за-модулем, где на КАЖДОМ шаге игра запускаема и
доказана бит-в-бит против v1. Инструменты уже есть — **локстеп-верификатор и
headless-харнесс** (tools/verify/ из этой сессии). v1 = золотой эталон.

- **Шаг 0 — render-драйвер первым, на данных v1.** Новый нативный Вектор-драйвер
  (сцена→экран), кормим сценой из состояния v1 (name-таблица v1 = tilemap, SAT
  v1 = sprites). Проверка: новый драйвер даёт ТОТ ЖЕ экран, что soft-VDP v1
  (пиксель-в-пиксель в headless). Render-слой доказан отдельно.
- **Шаг 1 — ядро модуль за модулем.** Загрузчик уровня → физика → по одному типу
  актёра (герой, мумия, нож). Каждый v2-модуль гоняем параллельно с v1 на одном
  вводе, локстеп сравнивает игровое состояние. Не интегрируется, пока не совпал.
- **Шаг 2 — нативные горячие рутины.** Звук ВИ53 и AI мумий → нативные, замеряем
  прирост Гц на каждом.
- **Шаг 3 — сжатие данных (ZX0/deexo).** Когда функционально готово — жмём
  графику/уровни, добиваем 16КБ.

Ничего не сливается, пока не сходится с эталоном.

## Портируемость (проверка дизайна)

Порт под новую машину = реализовать `render_frame` + `load_gfx` + `input_read` +
`sound_*` нативно. Ядро (Слой 1) и формат сцены (Слой 2) — не трогаются.
Порядок сложности порта KV: Эльф (HW-спрайты) < Вектор (готов первым) <
ПК-8000 (быстрый тайл-фон реж.1 + софт-спрайты) < Специалист (монохром) < БК
(PDP-11 — ядро переписывается, шов сцены тот же).

## Тестирование

- **Локстеп** (game-state бит-в-бит v2 vs v1) — регрессия логики.
- **Пиксель-компар** headless (экран v2-драйвера vs soft-VDP v1) — регрессия рендера.
- **Профилировка тактов** (счётчик инструкций/тик) — контроль движения к 50 Гц на
  каждом шаге; фолбэк «рендер через кадр на плотных сценах, логика 50» если не держим.
- Все прогоны в headless-харнессе + сверка с браузером (vector06js).

## Не в объёме (YAGNI)

- 8+ цветов (позже, если бюджет тактов позволит).
- Порты под другие машины (Слой 3) — отдельные спеки после готового Вектор-ядра.
- King's Valley 2 / доп. уровни.

## Открытые вопросы для реализации (в план)

- Точный бюджет тактов по частям (профилировать v1 первым шагом, чтобы знать
  реальный запас до 50 Гц и что именно нативить в первую очередь).
- Формат dirty (список vs битмап) — по факту профиля (обычно единицы клеток/кадр).
- Где на Векторе распакованные паттерны (свободное 0x4000-0x8000 vs видеотени).
