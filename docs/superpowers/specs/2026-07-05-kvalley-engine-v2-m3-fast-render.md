# King's Valley engine v2 — M3: быстрый рендер (POP-движок) → 50 Гц (дизайн-задел)

**Дата:** 2026-07-05
**Статус:** УТВЕРЖДЁН к реализации (M2c закрыт; ревью M2c ЗЕЛЁНОЕ). Инвариант M3: пиксель-компар ДЕРЖИТСЯ (тот же вывод, только быстрее).
**Родитель:** docs/superpowers/specs/2026-07-03-kvalley-engine-v2-design.md
**Референс:** docs/reference/OLDTOWER_ANALYSIS.md (Денис Грачёв, OldTower — нативный Вектор, 16 цветов, 50 Гц)
**Предшественники:** M1/M2a/M2b/M2c ✅ (все ревью SOUND/зелёные).

## Цель

Оптимизировать горячий рендер v2 (спрайты + восстановление фона + палитра), чтобы
он **влезал в окно vblank** и весь покадровый бюджет укладывался в **59904 такта
(50 Гц)** — убирая флик спрайтов и подёргивание экрана. Техника — **POP-движок**
OldTower (стековый блиттер). Игровая логика (M2b/M2c) НЕ меняется — рендер должен
давать ТОТ ЖЕ вывод (пиксель-компар держится), только быстрее.

## Обоснование (замер бюджета M2c-этапа)

Профиль v2-демо (движение, 4 спрайта): render_frame ≈ **73К тактов/кадр**
(draw_sprites 38К + restore фона ре-блитом 22К + erase 8К + палитра 2.4К),
build_sprites ≈ 25К, логика ≈ 1К. Итого ≈ **100К/кадр ≈ 30 Гц**, рендер ≫ окна
vblank (~10К) → спил в видимый кадр → флик + подёргивание. Узкое место — РЕНДЕР,
не логика. OldTower доказывает: нативный Вектор-движок держит 50 Гц POP-блиттером.

## Техники (из OLDTOWER_ANALYSIS.md)

1. **POP-блиттер** (§1): `di; ld sp,<данные>; pop de` — чтение 2 байт за 11 тактов
   (5 т/байт vs 14 у mov). Данные спрайта/тайла хранятся **interleaved по плоскостям**;
   запись в кадровый буфер с шагом плоскости +0x20 в старшем байте (`add b; ld h,a` = 2 такта).
   Для нашей 2-плоскостной 4-цветной схемы `pop de` берёт сразу 2 строки/данных.
2. **Saved-pixels restore фона** (замена ре-блита 22К): при рисовании спрайта сохранить
   байты фона под ним в буфер; при стирании — вернуть **стековой копией** (pop сохранёнки →
   push на экран), не ре-блит из паттернов.
3. **Pre-shifted спрайты** (§2 computed-entry + LUT): предвычисленные сдвинутые копии
   паттерна по X&7 — убирает вычисление сдвига/маски из горячего цикла. Обрезанные
   спрайты (край экрана) — computed-entry (патч младшего байта адреса перехода,
   страничное выравнивание, ноль ветвлений).
4. **Page-aligned LUT** (§3): y→адрес строки экрана, tile→адрес данных — без умножений.
5. **Render-list с готовыми адресами** (§4): пометка спрайта кладёт запись с УЖЕ
   вычисленным адресом; `draw` рисует список одним проходом под DI (сохранив SP).
   Только сдвинувшиеся/новые спрайты (мультиплекс-безопасно через порядок списка).
6. **Multiple-out палитра** (§5): писать каждый индекс палитры 6-8× `out (0Ch)` —
   на некоторых реальных Векторах плохая запись в цветогенератор (знание железа).

## Архитектура M3

Переписывается ТОЛЬКО драйвер `v2/driver_vector.asm` (render_frame + спрайт/фон-блит) +
подготовка данных (build_sprites/load_gfx кладут паттерны interleaved + генерят
pre-shifted копии). Контракт сцены (scene.inc) и логика (hero.asm/momias.asm) — НЕ меняются.

```
build_sprites -> render-list (готовые адреса, только изменённые спрайты)
render_frame (в vblank, под DI, SP-хак):
  1) restore фона под прошлыми спрайтами  <- saved-pixels стековая копия
  2) draw текущих спрайтов                <- POP-блиттер, pre-shifted, interleaved
  3) палитра (multiple-out, по флагу, не каждый кадр)
  восстановить SP; ei
```

## Пошаговая миграция (без регрессии; пиксель-компар = эталон)

Рендер должен давать БИТ-В-БИТ ТОТ ЖЕ вывод, что сейчас (планы == v1), только быстрее.
Каждый шаг: пиксель-компар держится + замер тактов падает.

- Saved-pixels restore фона (заменить 22К ре-блит) → пиксель-компар держится; такты ↓.
- Interleaved данные спрайтов + POP-блит draw (заменить 38К) → пиксель-компар; такты ↓.
- Pre-shifted LUT по X&7 → убрать сдвиг из цикла; такты ↓.
- Render-list + только-сдвинувшиеся спрайты → мультиплекс-безопасно; такты ↓.
- Multiple-out палитра по флагу.
- ГЕЙТ 50 Гц: замер render_frame < окна vblank И весь тик (логика+build+render) < 59904;
  браузер — флик и подёргивание ушли.

## Вне объёма M3 (следующее)

- ZX0-сжатие данных (M4) — отдельный майлстоун (§6 DeZX Городецкого готов).
- Rockman16-уровень (данные=код, RST8-разметка) — верхняя планка, пока НЕ нужна.
- Логика (M2b/M2c) — не трогаем.

## Тестирование

- **Пиксель-компар** (планы v2 == эталон) держится на КАЖДОМ шаге — рендер даёт тот же вывод.
- **Замер тактов** (профилировщик из этой сессии): render_frame по под-фазам + весь тик,
  цель render < vblank, тик < 59904.
- **i8080-чистота** (check_i8080.js) — POP/PUSH/DI/self-mod допустимы на i8080 (не Z80-only).
- **Браузер**: флик спрайтов и подёргивание лабиринта ушли; ощущается 50 Гц.
- **Реальное железо** (если будет): multiple-out палитра, тайминг vblank.

## Открытые вопросы для плана (после M2c)

- Раскладка interleaved-данных спрайтов v2 (наш 2-плоскостный 4-цветный формат vs
  4-плоскостный OldTower) и где их готовить (build_sprites vs load-time).
- Saved-pixels буфер: размер/адрес (96 байт × N спрайтов), порядок restore при перекрытии.
- SP-хак под DI в vblank: сохранение/восстановление SP, взаимодействие с RST7-ISR демо.
- Мультиплекс-безопасность «только-сдвинувшихся» (порядок render-list vs erase-all/draw-all).
- Оптимизация build_sprites (25К) — отдельно (pre-shifted снимает часть).
