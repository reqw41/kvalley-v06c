# KV нативный рендер — план Этапа 0-1

> **Для исполнителя:** реализовывать по задачам, каждая заканчивается независимо проверяемым
> результатом (сборка + honest-рендер + бюджет + long-run на зависание). Спек:
> `docs/superpowers/specs/2026-07-11-kv-native-render-engine-design.md`.

**Goal:** Получить flicker-free нативный рендер ГЕЙМПЛЕЯ (GameStatus=5): лабиринт из MapaRAM в
p0,p1 + спрайты из sprAttrib/enemyAttrib в выделенные p2,p3 — заменив soft-VDP фона и спрайтов,
сохранив рекомпилированную логику.

**Architecture:** Логика (рекомпиляция i8080) пишет игровое состояние в RAM (ACTOR, MapaRAM,
sprAttrib, enemyAttrib). Нативный рендерер в glue `kv_z80_to_8080.py` читает это состояние и
рисует прямо в плоскости Вектора, минуя MSX-VDP и тени.

**Tech Stack:** Python-рекомпилятор+glue (`tools/kv_z80_to_8080.py`), sjasm (Z80-мнемоника!),
Node headless-харнесс (vector06js), honest_render.js / frame_budget.js.

## Global Constraints

- Читать game-RAM в харнессе ТОЛЬКО через `memory.read(addr)` (банкинг Вектора), НЕ `memory.bytes[]`.
- grep .asm/.lst ТОЛЬКО с `LC_ALL=C` или `-a` (файлы latin-1).
- Визуал проверять ТОЛЬКО `tools/verify/honest_render.js` (реальный v06c.bmp).
- Проверять GS живым (`memory.read(GameStatus)`==5 геймплей) + SP в норме (~0x74xx-0x75xx) на
  long-run (≥2000 кадров) после КАЖДОЙ задачи — логика не должна ломаться.
- Z80-мнемоника в _VECTOR_RUNTIME (sjasm 0.39). В SP-хайджеке (POP-блит) НЕЛЬЗЯ call/push.
- **ПОРЯДОК КРИТИЧЕН:** нативный ФОН (освобождает p2,p3 от теней) идёт ДО нативных спрайтов
  (им нужны p2,p3). Иначе flicker-free невозможен (нет свободной плоскости).
- НЕ трогать игровую логику (chkControls/физика/ИИ/tickMain). Только render-рутины и glue.

**База:** чекпоинт `bf7570a` (ветка plane-split-overwrite), сборка:
`python3 tools/kv_z80_to_8080.py msx/kvalley_src.asm /tmp/kvv.asm --target vector && tools/bin/sjasm -s /tmp/kvv.asm <rom> /tmp/kvv.lst /tmp/kvv.sym`

## ЭТАП 1 — Нативный рендер: ПОСТРОИТЬ и ВАЛИДИРОВАТЬ (soft-VDP ЦЕЛ, ROM не меняем)

**Решение юзера (2026-07-11): soft-VDP оставляем на этом этапе (игра полностью рабочая), удаляем
его в ОТДЕЛЬНОМ следующем этапе ради освобождения памяти.** Значит Этап 1 — не трогаем рендер
рабочего ROM; строим нативный алгоритм рендера в JS-харнессе (читает game-RAM через memory.read)
и доказываем, что он даёт КОРРЕКТНУЮ картинку, сверяя с реальным экраном (honest_render soft-VDP).
Это прототип-валидация без риска для рабочей игры (прецедент: spike_r3.js рендерил из теней в JS).
