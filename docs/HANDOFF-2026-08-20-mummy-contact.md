# Передача: «зелёные точки» после контакта с мумией в верхнем ряду

Промпт для отдельного агента. Модель — **opus** (задача = найти ПРИЧИНУ дефекта и внести
правку, а не собрать таблицу чисел).

---

## Задача

Найти причину и починить дефект, который владелец видит на железе (MiSTer, ветка M):
**идём навстречу мумии по верхней строке, перепрыгиваем её, задевая краешком, — остаются
зелёные точки.**

## Где работать

Worktree `/private/tmp/kv-engine-cleanup`, ветка `shifthunt` (= `engine-cleanup`, они
совпадают). Репозиторий `~/projects/kvalley-v06c`. Сборка и деплой — `./build.sh`.

**Жёсткие ограничения:**
* НЕ поднимать `romCeil` (0x75A5 = 29861 байт). Сейчас свободно 259 Б.
* Только i8080, никаких `jr`/`ex af,af'` и прочего Z80. Гейт `check_i8080` следит.
* НЕ делать `git checkout` всего дерева — затрёт чужую незакоммиченную работу.
* Железо и деплой не трогать без разрешения владельца: на MiSTer лежит рабочая сборка.
* Коммитить КАЖДЫЙ законченный шаг отдельно, не копить в рабочем дереве.
* В сообщении коммита называть точную цену: байты образа и такты, раздельно по путям.

## Что уже известно (не переоткрывать)

Дефект воспроизведён детерминированно стендом `tools/verify/mummy_contact_probe.js`:

```
MUM=7 JP=8 node tools/verify/mummy_contact_probe.js
```

даёт стабильно 4 байта следа:

```
p1 X=184 стр=241 экран=10000000
p1 X=184 стр=242 экран=11000000
p1 X=184 стр=243 экран=11000000
p1 X=184 стр=244 экран=10000000
```

Развёртка по фазе прыжка (`JP=0..8`) на мумии 6 даёт ноль во всех фазах, на мумии 7 —
только фаза 8. То есть дефект РЕДКИЙ и фазозависимый; это нормально, не признак ошибки
стенда.

**Строки 241–244 — это ЗОНА ЗАВОРОТА СТОЛБЦА.** Столбец экрана — страница 256 байт,
`inc l` заворачивается внутри неё, и объект с `lo0 >= 241` занимает строки `lo0..255` И
`0..(lo0+15-256)`. Сюда попадает спрайт, частично ушедший ВЫШЕ поля: `lo0 = 239-Y`.

**Сегодня в этой же зоне закрыты ДВА дефекта того же класса** — восьмибитная арифметика,
врущая при заворот-переносе:
* `vec_su_fixup` (src/v06c/vec_blit.asm): `lo_b+15` переполнялся, тест решал «пересечения
  нет» и выбрасывал слот целиком. Это был другой баг владельца («половина спрайта остаётся»).
  Доказан гейтом `tools/verify/fixup_wrap_gate.js`.
* `vmx_ovl` (src/v06c/vec_sprout.asm): `l1+15` и `l0-15`, обе границы.

Сплошной аудит этого класса — `docs/AUDIT-2026-08-20-wrap-arithmetic.md`: **других мест с
восьмибитной арифметикой по строкам в движке нет**, девять оставшихся разобраны поимённо.

**Значит текущий дефект — ТРЕТИЙ механизм, и он НЕ в арифметике границ.** Отличие от
закрытых: здесь нет блита клетки, есть КОНТАКТ ДВУХ СПРАЙТОВ. Поэтому смотреть надо в
пару «герой + мумия»: непрозрачность (`vop_*`, `vhd_*`), стирание через AND-NOT
(`vsb_andn`, `vsa_row`), маску (`vsp_mask2`, `vtm_*`), микс пары (`vmx_*`, `vpr_*`, `vpz_*`).

Полезная зацепка: дедуп общей плоскости намеренно НЕ работает для слотов >= 6
(`ld a,(vec_nsp_idx); cp 6; jp nc, vsd_set` в vec_sprout.asm) — у мумий своя вторая
плоскость, и её никто не покрывает. Проверить, как это сочетается с заворотом.

## Чем мерить

`liveResidue()` внутри стенда — живая метрика без парковки: пиксель есть на экране, его нет
в чистой перерисовке комнаты из карты И он не накрыт НИ ОДНИМ действующим габаритом. Маска
строится по ОБЪЕДИНЕНИЮ старого габарита (шапка слота +0x00..+0x05) и нового (запись вывода
+0x96..+0x9B) плюс столбец с каждой стороны — слитая запись пишет ШИРЕ записи вывода.

Метрика уже проверена тремя способами и ей можно верить: 0 на штатной сборке во всех фазах,
576 Б при отключённом стирании, точный счёт впрыснутого следа (1 -> 1, 3 -> 3, 7 -> 7).

**НЕ пользоваться** метрикой с парковкой из `topright_jump_probe.js` как абсолютом: она
зависит от длины парковки (14/25/40 тиков дают разные числа) и годится только для сравнения
двух сборок при одинаковой парковке.

## Правила работы, оплаченные ошибками этой сессии

1. **Проверяй свой инструмент раньше, чем гипотезу.** За сессию трижды опыт оказывался
   ПУСТЫМ и выглядел как «гипотеза отвергнута»: питон-патчер молча не находил строку
   (`str.replace` не бросает), патч по метке не применялся, блок правки исчезал при откате
   коммита. Всегда `assert` на вставку и МАРКЕР в выводе самого прогона.
2. **Гейты читают образ из `build/kvalley_8c.rom`, а НЕ из аргумента командной строки.**
   Сравнение «база против правки» верно, только если ОБА образа собраны заново. Иначе
   сверяешься со старым файлом. Два образа из одного исходника различаются ровно тремя
   байтами метки версии.
3. **Гейт обязан падать на пустой выборке.** Если состояние не воспроизвелось — это отказ,
   а не «ОК». Пример — проверка в `fixup_wrap_gate.js`.
4. **Не называй разницу профилей ценой**, пока не повторил на неподвижной сцене либо не
   назвал метку поимённо: любая правка длительности тика уводит траекторию, и сборки играют
   РАЗНЫЕ сцены.
5. **Выравнивание.** Снятие кода ПЕРЕД `.align 256` образ не уменьшает (съедает паддинг), а
   добавление трёх байт может прыгнуть на целую страницу. Освобождающий коммит делай ОТДЕЛЬНО
   от тратящего — тогда видна настоящая цена каждого.
6. **Ручной вызов подпрограмм из стенда захватывает процессор**: сохраняй и возвращай PC, SP,
   регистры и флаги, иначе следующий тик уходит в никуда (стенд «виснет»).

## Что считать успехом

* `MUM=7 JP=8 node tools/verify/mummy_contact_probe.js` даёт 0 Б и вердикт OK;
* развёртка `JP=0..8` для мумий 6 и 7 — везде 0;
* `./tools/verify/run_gates.sh` даёт ТЕ ЖЕ вердикты, что до правки (сейчас пять провалов,
  все предсуществующие: `cheat_god_death`, `spr_resid_gate`, `door_fixup`,
  `door_leaf_purity`, `bonus_ending_gate`);
* `fixup_wrap_gate` остаётся зелёным;
* образ не выше `romCeil`, цена в байтах и тактах названа в коммите;
* сценарий владельца добавлен ГЕЙТОМ в `tools/verify/run_gates.sh`, с проверкой на пустую
  выборку.

Если по дороге выяснится, что причина не там, где ждали, — остановись и напиши, что именно
опровергнуто и чем. Отрицательный результат с доказательством ценнее правдоподобной правки.
