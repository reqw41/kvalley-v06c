# Заливка верхней клип-зоны уезжала за границу плоскости: разбор и правка

Дата: 2026-09-11. Ветка `3plane-composite25`, база `2e10704`, правка `4ab7caa`,
стенд `31c56ad`. Метка для слияний: **`3plane-composite25/clipzone-ncols`**.

**ВЕРДИКТ ОДНОЙ СТРОКОЙ.** `vtm_zclip` чистила фиксированные ЧЕТЫРЕ столбца вместо
ширины объекта и тем стирала фон лабиринта в чужом столбце 31 и в столбце 0 СОСЕДНЕЙ
плоскости; ширина взята из шапки слота (+5 Б, −517 тактов на вызов), перелив исчез
полностью, картинка изменилась ровно в двух клетках — тех, где база стирала лабиринт.

---

## 1. Механизм

`vtm_zclip` зовётся из `vtm_restore` (то есть в ПАЧКЕ, СЛЕДУЮЩЕЙ за отрисовкой), когда у
слота взведён MASK-флаг `+0xD4`. Она обнуляет строки fb `0xF0..0xFF` в трёх плоскостях
объекта; страницы плоскостей лежат в слоте `+0xF5/F6/F7` — их положил `vtm_setf5` в
момент отрисовки. Заливка идёт СТЕКОМ: `SP = (страница+1)*0x100`, восемь `push`
нулевой пары кладут 16 байт вниз, ровно строки `0xF0..0xFF` своего столбца.

Счётчик столбцов стоял константой:

```
	ld	b, 4	; 4 столбца клип-зоны
```

Ширина объекта (`ncols`) при этом 1..3 (буфер сдвинутого спрайта — 3 столбца, и
подготовка клипует ширину по правому краю экрана). Значит заливка ВСЕГДА чистила
на 1..3 столбца больше габарита, а у правого края уезжала за плоскость:

| объект | заливка чистит | что это |
|---|---|---|
| мумия `ncols`=2, `hi0`=0xBD (p1, столбец 29) | 0xBD, 0xBE | свои столбцы |
| | 0xBF | ЧУЖОЙ столбец 31 своей плоскости — правая стена лабиринта |
| | 0xC0 | столбец 0 СОСЕДНЕЙ плоскости (p2) — левая стена |
| объект на p2, столбец 29..31 | 0xE0 и дальше | СТРАНИЦА СЛОТА 0, служебные данные |

Почему граница плоскости не остановила: `push` инкрементирует SP ЦЕЛИКОМ, `0xBF+1 =
0xC0` — для стека это просто следующий адрес. Ровно этим же свойством пользуется сама
процедура (заворот `0xFF -> 0x00` объявлен безопасным в её шапке).

**ЗАМЕР НА ЖИВОЙ ИГРЕ (сборка ДО правки, `tools/verify/clipzone_live_gate.js`, 900
игровых тиков, сцена «мумии у правого края»):** 522 вызова заливки, из них 282 с
объектом в столбцах 28..31; **28 288 байт записано ВНЕ габарита**, из них **11 120 за
границу плоскости**. Свободная игра без принуждения сцены (1500 тиков) даёт 212 вызовов
и 20 затёртых НЕНУЛЕВЫХ байт — это уже не «ноль по нулю», а стёртая картинка карты.

Почему «стёртых ненулевых» на порядки меньше, чем «вне габарита»: затёртый нулём байт
остаётся нулём, и следующий перелив пишет ноль по нулю. Порча СЧИТАЕТСЯ ПО УНИКАЛЬНЫМ
АДРЕСАМ и **копится**: никто эти байты не перерисовывает.

Примеры из замера (значение ДО записи):

```
0xC0F1 было 0b11101111  (страницы bd/0/0,    ncols=2) — ЗА ГРАНИЦУ ПЛОСКОСТИ
0xC0F5 было 0b11111110  (страницы bd/0/0,    ncols=2) — ЗА ГРАНИЦУ ПЛОСКОСТИ
0x9FF1 было 0b11101111  (страницы bd/dd/9d,  ncols=2) — чужой столбец 31 своей плоскости
0xDFF5 было 0b11111110  (страницы bd/dd/9d,  ncols=2) — чужой столбец 31 своей плоскости
```

Дефект НЕ от композита: он есть и на `3plane-opt` (см. §7).

## 2. Правка

```
	ld	l, 3	; ncols ШАПКИ = ширина габарита, которым объект нарисован
	ld	a, (hl)
	or	a
	ret	z	; пустой габарит -> заливать нечего (иначе dec b дал бы 256 столбцов)
	ld	e, a	; E = счётчик столбцов; жив весь хайджек
	...
	ld	b, e	; было: ld b, 4
```

**Почему `ncols` ШАПКИ, а не записи вывода `+0x99`.** Заливка идёт в СЛЕДУЮЩЕЙ пачке:
запись вывода к этому моменту уже переписана подготовкой нового тика. Шапка (`+1` hi0,
`+2` lo0, `+3` ncols) описывает ровно нарисованное — на неё же опирается соседний
`vtm_restore`, снимая силуэт MASK с той же страницы `F5`.

**Доказательство «шапка == то, чем рисовали»** (а не рассуждение — перечислены ВСЕ пути
до `vtm_afterdraw`, их четыре, все в `vec_sprout.asm`):

* медленный путь — `vec_su_save` копирует запись вывода в шапку ДО отрисовки
  (`vso_sdone` -> `vec_spr_show` -> `vtm_afterdraw`);
* слитый путь — `vsm_shift` сам переводит шапку на новый габарит: пишет `+2` lo0,
  `+1` hi0, `+3` ncols, и с этого момента шапка описывает НАРИСОВАННОЕ (это же условие
  уже требует `spr_resid_gate` раздел D);
* путей, где сейва нет, ровно два (`pending>=2` скрытие и дедуп пары `pending=3`), и оба
  идут через `vsu_hide`, который обнуляет И `valid` шапки, И MASK-флаг `+0xD4`. Тогда
  `vec_su_restore` выходит ДО `vtm_restore`, и заливка не зовётся вовсе;
* статичная створка (`vso_static` пропускает сейв) — слоты 0..3, а `vtm_afterdraw`
  начинается с `cp 6 / ret c`: MASK им не ставится никогда.

**Почему клампа по границе плоскости не нужно.** Подготовка клипует ширину по правому
краю ЭКРАНА (`vsp_ncok`: `col0 + ncols <= 32`), а все три страницы объекта строятся от
ОДНОГО `col0`:

```
hi0  = vnc_pbase + col0
hi0b = vnc_dupb  + col0
hi0c = плоскость + (hi0 & 0x1F)
```

Значит `col0 + ncols <= 32` верно для КАЖДОЙ из трёх плоскостей, и заливка ровно
`ncols` столбцов от страницы плоскости физически не может выйти за её столбец 31.
Отдельная проверка стоила бы байт и тактов и была бы мёртвой.

**Вызывающие на «всегда 4» не опираются.** Единственный вызывающий — `vtm_restore`
(через самомодифицируемый `vsu_done+1`), он от ширины заливки не зависит. Копия буфера
в MASK (`vtm_adc`) берёт свои 32 байта = 2 столбца и к счётчику заливки отношения не
имеет; ANDN силуэта (`vtm_restore`) считает свою ширину сам как `min(ncols шапки, 2)`.

## 5. Остался ВТОРОЙ дефект той же процедуры — строки, а не столбцы (НЕ ЧИНИЛСЯ)

Заливка чистит строки `0xF0..0xFF` **независимо от того, где по вертикали стоит
объект**. Замер (сборка ПОСЛЕ правки, свободная игра 1500 тиков) — 8 затёртых
НЕНУЛЕВЫХ байт, все с такой атрибуцией:

```
порча 0x9FF1..0x9FF7, 0xDFF1/0xDFF5   lo0 шапки = 104, ncols = 3, hi0 = 0xBD
```

То есть объект стоит в СЕРЕДИНЕ поля (fb 104..119), а заливка всё равно стирает верхние
две строки знакомест поля (fb 255..240) в его столбцах. Это тоже накопительная потеря
пикселей, и на базе она была ЗАМАСКИРОВАНА: те же байты успевал уничтожить перелив по
столбцам. Итог по свободной игре (1500 тиков): база — 10 затёртых байт (2 в столбце 0
через границу плоскости, 8 в столбце 31), после правки — 8 (только столбец 31, СВОИ
столбцы объекта). Множество испорченных адресов после правки — строгое подмножество.

**Что с этим делать (не сделано намеренно — это отдельное изменение поведения).** В
первой версии процедуры (`959a9c0`) стоял гейт «объект достаёт до клип-зоны»:
`lo0 >= 224 -> иначе выход`. Он потерялся при переносе ветки (`f7463a7` уже без него).
Восстановление стоит ~6 Б (`ld l,2 / ld a,(hl) / cp 224 / ret c`, lo0 брать из ШАПКИ) и
ещё сокращает пачку, но требует заново доказать `top_overlap_resid`, `knife_momia_resid`
и `spr_resid_gate` — ради них клип-зона и появилась. Отдельная задача.

# ЧАСТЬ II. Второй дефект: заливка чистила клип-зону объекту, который до неё не достаёт

Дата: 2026-09-11 (вечер). База `8080473`, правка `4ed7ef7`, стенды `a16a9d4` и `f6145e1`.
Метка для слияний: **`3plane-composite25/clipzone-lo0`**.

**ВЕРДИКТ ОДНОЙ СТРОКОЙ.** Гейт вернуть МОЖНО, но НЕ «как было»: верная граница —
`lo0 >= 225` (пересечение габарита `lo0..lo0+15` со строками 240..255), а не 224
(959a9c0, на единицу щедрее) и не 228 (2b042f7, РЕЖЕТ ЖИВОЕ — замер даёт 208 законных
вызовов с `lo0` = 225/227); от возвращённого гейта не покраснел ни один из трёх
сторожей — их числа совпали с базой до единицы, — а вся заливка у объектов из середины
поля (23 824 Б за 900 тиков сцены и 37 984 Б за 1500 тиков свободной игры) исчезла.

## 1. Зачем заливка нужна вообще и кому она не нужна

`vtm_zclip` обнуляет строки fb `0xF0..0xFF` (два верхних ряда знакомест ПОЛЯ) в
столбцах объекта. Клип-зона существует потому, что у самого верха геометрия объекта
**прижата**: `vclp` (`vec_sprout.asm`) при `lo0 >= 249` клампит габарит к `lo0 = 248` и
сдвигает данные спрайта внутри буфера, выталкивая верхние строки. Сейв/восстановление и
ANDN силуэта работают по прижатому габариту, а в fb остаётся сирота — её и снимает
заливка грубой силой.

**Кому она не нужна — доказательство, а не рассуждение.** Всё, что объект нарисовал,
лежит в строках `lo0..lo0+15`: этим же `lo0` ШАПКИ (+2 -> `vsb_lo`) соседний
`vtm_restore` снимает силуэт MASK через `vsb_andn`, и по нему же идёт POP-восстановление
фона. Строк вне габарита объект не касался ни в этой пачке, ни в предыдущей (шапку в
момент отрисовки переводит на новый габарит `vsm_shift`/`vec_su_save` — перечисление всех
четырёх путей см. в §2 части I). Значит вне габарита заливке снимать НЕЧЕГО, и
единственное, что она там делает, — **стирает фон лабиринта**, который никто не
перерисовывает.

## 2. Выбранное условие и почему именно оно

Габарит объекта по вертикали — РОВНО 16 строк `lo0..lo0+15` (все шесть петель работы с
fb развёрнуты на 16, см. шапку `vsb_or`). Клип-зона — строки 240..255. Пересечение
непусто ровно при `lo0 + 15 >= 240`, то есть **`lo0 >= 225`**.

* `lo0 = 224` -> габарит 224..239, клип-зоны НЕ касается. Порог 224 (первая версия,
  `959a9c0`) на единицу щедрее нужного — не ошибка, но и не граница.
* **ЗАВОРОТ УЧТЁН И БЕЗОПАСЕН.** `vclp` гарантирует `lo0 <= 248`, поэтому завёрнутый
  габарит (`lo0` = 241..248) — это строки `lo0..255` плюс `0..(lo0+15-256)`; часть
  `lo0..255` целиком лежит в клип-зоне, и гейт `lo0 >= 225` такой объект пропускает.
  Отдельной ветки «а вдруг заворот» не нужно: условие `lo0 >= 225` покрывает и её.
* **ПОРОГ 228 БЫЛ БЫ РЕГРЕССОМ.** `knife_momia_resid` даёт 189 вызовов с `lo0 = 225` и
  19 с `lo0 = 227`; `top_overlap_resid` — ещё 2 с `lo0 = 225`. Все они клип-зону реально
  задевают, и порог 228 (`2b042f7`, `vtm_afterdraw`) отрезал бы их.

**Что гейт НЕ делает и почему (сознательное решение).** У объекта, который до зоны
ДОСТАЁТ, заливка по-прежнему чистит ВСЮ зону 240..255, а не только пересечение с
габаритом. Это «запас», и он намеренный: клип-зона — область прижатой геометрии, сирота
остаётся от НЕДАВНЕЙ позиции объекта, и запас её накрывает. Цена запаса теперь
измеряется: 1518 Б за 900 тиков сцены при **0 Б порчи** на этой ветке и 3260 Б при
**1 Б порчи** на `3plane-opt`. Это третий, на два порядка меньший дефект того же класса;
он открыт с числами, а не закрыт молча.

## 3. Почему гейт исчез (история, чтобы не «восстановили как было»)

| коммит | что стало с гейтом |
|---|---|
| `959a9c0` | гейт `lo0 >= 224` ВНУТРИ `vtm_zclip` (читал lo0 записи вывода, +0x98) |
| `2b042f7` | гейт ПЕРЕНЕСЁН в `vtm_afterdraw` как `lo0 >= 228`: заливка осталась без проверки, но и не звалась, пока MASK не взведён |
| `7d07a2c` | из `vtm_afterdraw` проверка СНЯТА вместе со сменой гейта индекса 4 -> 6 («герою MASK нельзя: шлейф при ходьбе и сорванная одежда у створки»). С этого момента MASK ставится мумии/ножу на ЛЮБОМ Y, и заливка поехала по всему полю |

Сообщение `7d07a2c` перечисляет три починки (`vop_eff`, `vhr_one`, `vsd_nm2`) и замеры к
ним; снятия порога `lo0` оно не упоминает и замером не подпирает. **То есть гейт не
отменяли по результату — его потеряли при переносе.** Причина, ради которой его «когда-то
сняли», не существует: сняли не его, а ПОРОГ MASK'а, и MASK на любом Y остаётся в силе —
изменилась только заливка.

### 5.3 `top_overlap_resid.js` — СТЕНД БЫЛ СЛЕП, ПОЧИНЕН (коммит `f6145e1`)

**Это находка, а не побочная правка.** На базе `8080473` гейт выходил с кодом 3
«инструмент слеп» (подсажено 5, видит 0) ЕЩЁ ДО первой сцены — то есть три семейства
(legacy / parallel / mumJump) не прогонялись вообще, и «сторож» ничего не сторожил.

Причина — не слепота сравнения, а **перекраска метки**: она ставилась ДО `residue()`,
то есть до двенадцати тиков парковки. Атрибуция писателя по PC: `0x4B37` = `vbt8_cp`,
ТАЙЛОВЫЙ БЛИТТЕР лабиринта — анимация ворот пирамиды 1 доходит до столбца 16 на ШЕСТОМ
тике парковки и кладёт туда законный фон (замер: метка цела на тиках 0..5, обнулена с
тика 6; подсадка во все 96 «столбец x плоскость» на тех же строках не выжила НИГДЕ).

Починка: `residue(inject)` зовёт подсадку между последним тиком парковки и `grab()`.
Проверяемый инструмент — «снимок TEST + эталон `vec_nat_room` + классификация»; парковка
относится к СЦЕНЕ. Негативный контроль цел: следом идёт `residue()` без подсадки и обязан
дать d=0 (даёт).

неё зона и шире габарита) — то есть это отдельная задача с собственным замером, а не
дописывание условия. Порядок величины — единицы байт против 23 824, снятых здесь.
