# План: King's Valley (i8080) на ванильный Вектор-06Ц

> Цель: наша i8080-трансляция King's Valley (сейчас использует MSX-VDP, работает на openMSX)
> должна пойти на **ванильном Векторе-06Ц** — заменой MSX-видео/звука на нативный слой Вектора.
> Статус входа: игровая логика ПРОВЕРЕНА на openMSX (мумии ходят/гибнут/возрождаются, звук, нож).

## Ключевой факт (из анализа Z80-порта Городецкого)

Порт Городецкого (`roms/kvalley_z80.rom`, 14662 б, 2008) **не эмулирует TMS9918** — он ещё в 2008
заменил MSX-видео на нативный Вектор:
- кадровый буфер: **4 плоскости × 0x2000, база 0x8000**;
- блиттер: **0x12E4** (8-байтные полосы в плоскости; A=H&0x3F выбирает плоскость: 0x38→0x2000,
  0x39→..., 0x3A→0x3000), рабочий буфер глифов 0x2000-0x3FFF;
- палитра: рутина **0x10D8** (128× `out 0x0C`, данные 0x10A2), порты PPI `out 0x00..0x04` (режим/скролл/бордюр);
- звук: **AY 0x14/0x15** (или ВИ53);
- vblank: **RST7 (вектор 0x38), ISR 0x01DF** гоняет и блиттер, и звук.

Значит «драйвер VDP» извлекать неоткуда — вместо него готовый нативный рендер King's Valley под Вектор.
Он вшит в бинарь (данные размазаны по низкому ОЗУ → бинарную рекомпиляцию порта проект отбросил), НО есть
**полный побайтно-точный дизасм** `build/kv_faithful.asm` — донор примитивов.

## Архитектурное решение

**Стратегия (директива юзера): сначала МЕДЛЕННЫЙ, но НЕЗАВИСИМЫЙ VDP-движок — довести до
работоспособности, потом оптимизировать.** Независимый = гейм-агностичный эмулятор VDP (не завязан на
конкретные рутины King's Valley и не на код Городецкого): держит виртуальную VRAM (16К) + регистры VDP,
и раз в кадр (из vblank-ISR) РЕНДЕРИТ её в плоскости Вектора. Оптимизация потом (инкрементальный
write-through, выделенные спрайт-плоскости) — БЕЗ переписывания, т.к. движок параметризован.

**Чокпоинты доступа к VDP** (немного, редиректим в шим — у нас читаемый исходник):
SETWR/`setVDPWrite` → указатель записи; `out (98h)`/WRTVRM → запись в вирт. VRAM + инкремент;
RDVRM → чтение; WRTVDP → регистр VDP (таблицы фиксированы как константы — приём Aleste — почти игнор);
запись атрибутов спрайтов идёт в вирт. VRAM 0x3B00 тем же путём. Реализация — ветка
`_apply_vector_glue()` в `kv_z80_to_8080.py` (вместо MSX-glue: без slot-switch/0x98/BIOS-видео).

### КЛЮЧЕВОЙ ПАРАМЕТР: конфигурируемое разбиение плоскостей (фон/спрайты)
На Векторе 4 бита пикселя (по 1 из каждой плоскости) → индекс 16-цв. палитры. Движок с самого начала
параметризован маской плоскостей фона и маской плоскостей спрайтов; палитра настраивается под разбиение
так, чтобы спрайтовые биты «перекрывали» фон. Это ось скорость↔цвет:

| фон/спр | цветов фона | цветов спрайта | оверлей спрайта |
|---|---|---|---|
| 4/0 | 16 | любые | save/restore фона (МЕДЛЕННО, общий — СТАРТ) |
| 3/1 | 8 | 1 (моно) | «бесплатно» (чистим/рисуем только спрайт-плоскость) |
| 2/2 | 4 | 3+прозр. | «бесплатно» |
| 1/3 | 2 | 7+прозр. | «бесплатно» |

СТАРТ = 4/0 (save/restore, работает для любой игры/цветов). Оптимизация King's Valley → вероятно 3/1
(8 цв. фон + моно-спрайты, оверлей без save/restore). Смена = только конфиг + перекладка палитры.

**Слои движка** (модульно — тайл-часть переиспользуема для бесспрайтовых MSX/ZX-портов):
- (а) VDP-адресация/VRAM-шим (чокпоинты выше);
- (б) тайл-фон SCREEN2 (name+pattern+color) → плоскости фона;
- (в) **спрайт-движок** (16×16, режимы save/restore ИЛИ выделенные плоскости) — параметризован разбиением;
- (г) **палитра** (порт 0x0C) — движок ЗАДАЁТ её сам, вычисляя из двух вещей: (1) маппинг 16
      фиксированных цветов MSX SCREEN2 (TMS9918) → палитра Вектора; (2) раскладка под текущее разбиение
      плоскостей, чтобы спрайтовые биты перекрывали фон (напр. 3/1: записи 0-7=цвета фона, 8-15=цвет
      спрайта). Меняется вместе с разбиением; перезагружается покадрово при необходимости (защёлка
      палитры Вектора — по кадру);
- (д) звук: PSG(AY) → AY 0x14/0x15 (почти перемаппинг; MSX PSG = AY-3-8910), либо `tools/ay2vi53.py`.

Плоскостные примитивы (блит в плоскость, палитра) можно взять донором из порта Городецкого
(`build/kv_faithful.asm`: блиттер 0x12E4, палитра 0x10D8) ИЛИ написать заново — на медленном старте
проще написать чисто, донор подключим при оптимизации.

## Карта памяти Вектора и бюджет (замерено, Фаза 0)

Жёсткое ограничение: **кадровый буфер 0x8000-0xFFFF (32К, 4 плоскости × 8К)** сканируется как экран →
код+данные+стек+шадоу должны уместиться в **0x0000-0x7FFF (32К)**. Плоскости: P0 0x8000, P1 0xA000,
P2 0xC000, P3 0xE000.

Замеры нашего i8080-билда:
- код+данные (вкл. всю графику как `db`) = **22.7К** (0x4000-0x9AD5);
- work RAM MAP сейчас 0xE000-0xF000 (~4К) + стек 0xE700 — **КОЛЛИЗИЯ с плоскостью 3**, переносим.

Векторная раскладка (цель):
- код+данные ребейз 0x4000→**0x0100** (или 0x0000): 0x0100-0x5C00 (~22.7К);
- work RAM + драйвер + шадоу + стек: **0x5C00-0x7FFF (~9.5К)** — влезает (~8К нужно);
- буфер 0x8000-0xFFFF — только видео.
- **Графику НЕ шадоуим** (нет места на 12К pattern+color): рендер write-through читает паттерны прямо из
  ROM-блоков (запоминаем указатель ROM-источника при init-загрузке `DEtoVRAM`→VRAM 0x0000/0x2000/0x1800).
  Динамические шадоу малы: name table (768Б, тайл-карта), атрибуты спрайтов (128Б).
  ⇒ вместо «полной виртуальной VRAM» — write-through из ROM + малые шадоу (memory-frugal, всё равно
  гейм-агностично для SCREEN2 с контигуозным тайлсетом).

## Поверхность MSX-железа для замены (замерено)

| MSX BIOS | адрес | call-сайтов | → Вектор |
|---|---|---|---|
| WRTVRM | 0x4d | 19 | write-through в буфер/шадоу |
| WRTPSG | 0x93 | 6 | AY 0x14/0x15 (тот же чип) |
| RDVDP | 0x13e | 3 | флаг vblank Вектора |
| WRTVDP | 0x47 | 2 | видеорежим (таблицы фикс. — приём Aleste) |
| SETWR / SETRD | 0x53 / 0x50 | 1 / 1 | указатель записи/чтения VRAM |
| RDVRM / RDPSG | 0x4a / 0x96 | 1 / 1 | чтение шадоу / AY |

Плюс: прямой `out (98h),a` (3 наши VRAM-цикла) → запись данных VRAM; клавиатура (SNSMAT) → 8255 порт 0x00;
прерывание H_TIMI-хук → **RST7 (0x38)** ISR. Редирект: переопределить BIOS-`equ` на наши Вектор-рутины
(включаемые в билд ветки `_apply_vector_glue`), т.е. поверхность мала и перечислима.

## Фазы

## СТАТУС: Шаг 1 (ребейз+вход+RST7+звук) — ГОТОВО (2026-07-01)

`kv_z80_to_8080.py msx/kvalley_src.asm out.asm --target vector` → `_apply_vector_glue`: ребейз к 0x0100,
вектор-страница (JP startCode @0, JP vec_isr @0x38, паддинг `ds`), work RAM 0xE000→0x6800, редирект BIOS
на Вектор-рутины (метки, не equ), RST7-ISR с сохранением 9 теневых ячеек, PSG→AY 0x14/0x15, RDPSG/SNSMAT
= idle. Собран `roms/kvalley_vector.rom` (32К, код 0x100-0x5C4D, work RAM 0x6800, стек 0x6F00). Стенд:
`node tools/vec_probe.js` (реальный vector06js).
ПРОВЕРЕНО на модели Вектора: грузится, краха нет; **runGame крутится каждый кадр** (timer++, waitCounter--,
tickInProgress осциллирует); RST7 работает; **звук идёт в AY** (тысячи записей); буфер чист (work RAM не на
0xE000). ГРАБЛЯ: `_apply_vector_glue` сперва не добавил cell-save обёртку → реентерабельность вернулась
(tickInProgress завис) → вложил save/restore 9 ячеек в vec_isr. ГРАБЛЯ: RDPSG-стаб читал AY→фантомный
джойстик → меню сбрасывало счётчик → RDPSG=0xFF (idle). ОЖИДАЕМО: автомат застревает на анимации лого
(состояние 0, `dibujaLogo` рисует в VRAM) — видео-зависимость, разблокируется Фазой видео (2-4), НЕ баг glue.
ДАЛЕЕ: Фаза 3 (тайл-фон) → анимации/автомат оживут.

## СТАТУС: Фаза 2 (палитра) — ГОТОВО (2026-07-01)
Портирована рутина палитры Городецкого (0x10D8) в Вектор-runtime `vec_setpal`: `out (00h),88h` (режим 8255),
затем на 16 записей `out (02h),index` + `out (0Ch),color`×8 (тайминг записи палитры). Данные — 16 байт
Городецкого. Вход теперь `jp vec_init` (палитра → startCode). ПРОВЕРЕНО на стенде: `io.Palette` = верные
цвета (entry2/3=песок кирпичей, entry8-11=красный мумий, entry4-7=серо-синий). Экран пока чёрный (entry0=0
+ пустой буфер) — палитра готова к тайлам. Инструмент: `tools/bin/sjasm` (сохранён в проект, /tmp чистится).

## ЛОКНУТЫЙ ДИЗАЙН ВИДЕО (Фаза 3, готово к реализации)
- **Графика RLE-сжата** (`unpackGFX` распаковывает в VRAM) → рендерить из ROM нельзя, нужен распак-шадоу.
- **`UnpackPatterns` грузит ОДИНАКОВЫЕ данные в 3 банка SCREEN2** → шадоу нужен только 1 банк:
  паттерны 0x0000-0x07FF (2К) + цвета 0x2000-0x27FF (2К) + name table 0x3800 (768Б) = **~4.8К, влезает**.
- **Раскладка буфера Вектора** (render_vram): адрес_в_плоскости = `(X>>3)*256 + (255-Y)`, бит = `0x80>>(X&7)`;
  плоскость p @ `0x8000+p*0x2000`. 8 гориз. пикселей строки тайла = ОДИН байт на плоскость (4 байта/строку).
- **Алгоритм тайл-блита** (блочная графика, 8×8): для строки py тайла: pat=шадоу[patBase+tile*8+py],
  col=шадоу[colBase+tile*8+py], fg=col>>4, bg=col&15; для плоскости p: fgb=(fg>>p)&1, bgb=(bg>>p)&1 →
  planebyte = (fgb?pat:0) | (bgb?~pat:0); записать 4 байта в плоскости @ col_cell*256+(255-(row*8+py)).
- **Чокпоинты→шадоу**: `setVDPWrite`/SETWR → указатель; `WRTVRM`/`out(98h)` → запись в шадоу (только банк0
  адреса 0x0000-0x07FF паттернов, 0x2000-0x27FF цветов, 0x3800+ name table; прочее игнор); при записи
  name table → блит тайла (write-through) ЛИБО полный проход по name table раз в кадр из RST7-ISR.
- Донор блит-примитива при желании: блиттер Городецкого 0x12E4 (`build/kv_faithful.asm`).

### Фаза 0 — Векторный стенд
- Завести i8080-трансляцию под модель Вектора (`tools/z80vector.js`/`v06_playtest.js`/`machine.js`) вместо openMSX.
- Голден-референс = кадры Z80-порта Городецкого через `z80vector.js`.
- **Итог:** ROM грузится на модели Вектора, снимаем дамп VRAM 0x8000 → PNG (`tools/render_vram.py`).

### Фаза 1 — Звук (быстрый выигрыш)
- Перемаппить PSG (WRTPSG=0x93 / `out 0xA0/0xA1`) → `out 0x14/0x15` (тот же чип AY).
- **Итог:** джингл/SFX на Векторе; сверка регистров AY с openMSX-базлайном (vol A=0b B=0c на GS=4).

### Фаза 2 — Палитра + база кадра
- Заменить `SetVideoMode`: настроить режим Вектора + залить палитру (перенести 0x10D8/0x10A2 Городецкого
  ИЛИ маппинг 16 цветов MSX→Вектор через порт 0x0C). Очистить/инициализировать буфер 0x8000.
- **Итог:** верный фон/палитра.

### Фаза 3 — Тайл-фон SCREEN2 → плоскости
- Заменить `setVDPWrite`/`setFillVRAM`/`DEtoVRAM`/`drawRoom`: write-through в виртуальную VRAM + блит
  изменившегося 8×8 тайла (pattern+color → 4 плоскости). Плоскостной примитив — донор блиттера 0x12E4.
- **Развилка:** рисовать MSX-данные напрямую (гейм-агностично) vs переиспользовать конвертированную графику
  Городецкого (быстрее, но привязка к формату). Решить здесь.
- **Итог:** пирамида/комнаты рисуются на Векторе (статично).

### Фаза 4 — Спрайт-композитор (тяжёлый, King's-Valley-специфичный)
- Перехватить запись таблицы атрибутов спрайтов (VRAM 0x3B00) + генератора (0x1800): программные спрайты —
  save фона под спрайтом, маск-блит 16×16 с прозрачностью, restore при движении.
- Технику save/restore/blit реверсим из порта Городецкого (он рисует бегущих мумий нативно).
- **Итог:** игрок/мумии/ножи/облако движутся на Векторе.

### Фаза 5 — Интеграция + тайминг
- Оформить Вектор-glue в `kv_z80_to_8080.py`; рендер гонять из RST7-vblank ISR (аналог 0x01DF).
- Сверка полного демо на vector06js с поведением openMSX (мумии двигаются/гибнут/возрождаются, звук).
- Профилировка бюджета кадра (dirty-rects; урок из порта — инкрементальный блит, не полный рескан).

### Фаза 6 — Упаковка/железо
- Собрать Вектор-.rom, проверить в браузере (vector06js) — ссылка на проверку.

## Риски/развилки
1. **Скорость на 3 МГц** — главный риск (у Aleste было 8 МГц). Митигация: только инкрементальный рендер;
   King's Valley графически умеренна.
2. **Формат графики** (Фаза 3): MSX-данные напрямую vs конвертированная графика Городецкого.
3. **Извлекаемость спрайт-кода Городецкого** (Фаза 4): если размазан — пишем свой композитор, порт как справка.
