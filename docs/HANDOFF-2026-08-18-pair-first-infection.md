## ОТКРЫТЫЙ ДЕФЕКТ: «зелёная точка» при перепрыгивании мумии на верхней строке

Жалоба с железа: при перепрыгивании героем мумии на верхней строке в редкие моменты
проскакивает точка «от зелёной мумии». Ловится в god-mode (чит G).

### Механизм (доказан watchpoint-трассой, tools/verify/topjump_live_probe.js)

Это не мумия — это КОЖА ГЕРОЯ (p1-only = idx4 = зелёный). Родовой дефект «пара
рисуется в пачке ПЕРВОЙ» (антифликер героя, ЗАДАЧА#50/#53):

- В slow-пачке (перекрытие пары и мумии: общая плоскость p1 у кожи и мумии слота 7)
  порядок: vpr_sout пары (restore-save-show) -> vso_rloop (restore остальных) ->
  vso_sloop/dloop (save по фронту + show остальных).
- save МУМИИ идёт ПОСЛЕ show пары -> её p1-блок фона захватывает КОЖУ героя
  (симметрично p2-блок — одежду; p0-блок пары ловит мумию — этот вынос закрыт vop_eff).
- Каждый restore мумии выплёвывает кожу-призрак как «фон». Пока герой рядом, поверх
  сразу рисуются герой/мумия — незаметно. Когда герой отлетел (вершина прыжка,
  py=3..8, спрайт в клипе) и мумия сдвинулась — куски остаются видимыми несколько
  тиков, пока их кто-нибудь не затрёт.
- Репро: topjump_live_probe.js 400 --m2 --tight: t=342..347, p1 col=15 lo=234..238.
  ВАЖНО: zclip (vtm_zclip) зануляет только lo 240..255 — выплев на lo 234..239 голый.

### Кандидаты фикса (по убыванию правильности)

A. Вычистить вклад пары из блоков соседа после его vec_su_save (vso_sloop):
   ANDN буферами пары (слоты 4/5, +0xA0) по пересечению габаритов, с выравниванием
   столбцов и lo0. ~70 Б — нужны дубли из dup_scan (остались: momiaSuicida/
   momiaDesaparece 12Б, DEtoVRAM/vec_cache_wr 12Б, vip_np/vec_isr_nested 12Б,
   vec_isr_nr/nested 11Б, dt_vec_draw/text_blit/konami_text 14Б, KonamiLogo-тройка 14Б,
   smk_blk/smk_lo 9Б). Скан: node <scratch>/dup_scan.js (git show bbdaeb2:tools/verify/dup_scan.js).
B. При пересечении пары с соседом (vmx_j это уже находит) выводить пару НЕ первой:
   vpr_mix=0xFE + не звать vpr_sout -> пара идёт общим потоком с фронтом (инвариант
   восстановлен). ~10-15 Б, НО возвращает «герой мерцает при перекрытии» (718/718
   попаданий луча в дыру героя были ровно в этих пачках — см. шапку vmx_check).
   Компромисс: мерцание против точек.
C. Точечно для мумий: расширить MASK-restore (vtm_restore) гашением... не работает —
   мусор ВНЕ силуэта мумии.

## Инструмент: полный дамп состояния из Devector (2026-08-19)

В форке ~/Projects/devector-fork добавлена команда **«Devector: Dump State (RAM + regs)»**
(`devector.dumpState`, src/extention/cmd_dump_state.ts): пишет рядом с проектом
`dump-<ts>.bin` (64 КБ ОЗУ) + `dump-<ts>.json` (регистры/PC/SP/флаги/такты).
Только чтение (GET_MEM_RANGE + GET_CPU_STATE) — пауза не сбивается, снимать можно
прямо на остановленном кадре с артефактом. Собран пакет `devector-dumpstate.vsix`.

Зачем: штатная панель Memory Dump показывает 256 байт за раз, полного экспорта в
плагине нет. С .bin состояние загружается в стенд vector06js (beam_harness) —
`memory.bytes.set(dump)` — и артефакт разбирается пошагово с watchpoint'ами вместо
синтетических репро, которые владельческие сценарии пока не воспроизводят.

## Инструмент 2: «чёрный ящик» Devector (2026-08-19)

Форк ~/Projects/devector-fork, пакет `devector-blackbox.vsix`. Три команды:
- **Devector: Recorder Start/Stop** — кольцевой буфер последних N секунд (10/5/20/30,
  50 к/с): каждый кадр снимок 64 КБ ОЗУ в ПРЕДВЫДЕЛЕННОЕ кольцо (аллокаций в кадровом
  цикле нет; 10 с = 500 кадров = 32 МБ). Хук — emulatorUI.tick, сразу за EXECUTE_FRAME.
- **Devector: Recorder Save** — выгрузка ПРЕДЫСТОРИИ: `rec-<ts>.bin` (кадры подряд по
  65536 Б, от старого к новому) + `rec-<ts>.json` (seq/cc/pc/sp по кадрам).
- **Devector: Dump State** — разовый снимок (RAM+regs), паузу не сбивает.

Разбор: `node tools/verify/load_devector_rec.js rec-*.bin [--last N] [--slot 6]`.
Ищет «ПРИЛИПШИЕ» биты: зажглись в кадре i и дожили до конца записи, минус габариты
живых спрайтов последнего кадра. Печатает первый такой кадр с PC/тактами — это и есть
точка расследования; --slot печатает шапку/запись вывода слота по кадрам.
Самопроверка: подсаженный в кадр 30 байт 0x3C (p2, X=64, lo=200) найден ровно один раз,
без ложных срабатываний от стоящего героя.

ПОЧЕМУ ЭТО РЕШАЕТ ТУПИК: артефакт замечают ПОСЛЕ появления, а причина живёт кадрами
раньше; синтетика владельческие сценарии не воспроизводит. Теперь причина берётся из
реальной партии: кадр рождения мусора -> состояние слотов в нём -> watchpoint в стенде.
