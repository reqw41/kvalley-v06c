# Задача: прототип упрощённого вывода мумий (King's Valley, Вектор-06Ц) — скорость ценой визуала

## Контекст
`~/projects/kvalley-v06c` — порт King's Valley (Konami, MSX) на ванильный Вектор-06Ц, i8080 3 МГц. Живая линия — ветка `3p`
(worktree `~/projects/kvalley-v06c/3plane-composite25`): фон в трёх плоскостях, спрайты композитом поверх, сохранение фона
под объектом (save-under), сдвиг по X на 8 фаз, ожидание луча (BEAMW) против мерцания. Цель — 25 Гц (шаг = 2 кадра), но в
тяжёлых сценах шаг идёт 3–4 кадра. Журнал — `docs/JOURNAL.md`; разложение шага — `docs/tick_breakdown/REPORT.md` и
`ADDENDUM_1.md` (`node tools/verify/tick_breakdown.js`).

**Куда уходит шаг (стресс «герой + две мумии наверху», ~111 тыс. тактов/шаг):** подготовка спрайтов ~71 тыс.
(`vec_spr_prep` ~44,7 тыс.: обвязка — клип, указатели, развилки, буферы — ~26 тыс.; перекрытия `vop_*/vom_*` ~8,8 тыс.;
маски ~3,6 тыс.; сборка/записи ~4,6 тыс.; сам сдвиг RRCA ~1 тыс.; плюс `vsp_fastmark`, `vpr_scan`, сортировка), логика Konami
~24,6 тыс. На объект — 9–13,5 тыс. тактов подготовки за шаг. Сдвиг дешёвый: грубее X — бесполезно. Кэш сдвигов — в стрессе
0–2,5 % повторов и нет памяти.

Опыт порта Montezuma (`~/projects/monty-v06c-main`, fix31): враги «по схеме ZX» — одна плоскость, одна краска, без
сохранения фона; стирание — перерисовкой клеток фона по карте (тайлы из кэша), горизонтальное замещение. Там это дало
скорость без мерцания и пропаданий.

## Что сделать (прототип, без внедрения в 3p)
Работайте в отдельном worktree и ветке `mummy-zx` от текущей `3p`. **Сборка только `KV_NO_DEPLOY=1 ./build.sh`** — без
заливки на MiSTer и без перезаписи `~/projects/vector06js/kv8c.rom` (был случай). Не пушить.

**Вариант A — мумии одной плоскостью.** Мумии (и при желании нож/искры — оцените отдельно) выводятся в одну плоскость одной
краской (выберите плоскость/палитру так, чтобы мумия читалась поверх фона), без 3-плоскостного композита и save-under;
стирание — перерисовкой клеток фона, которые занимала мумия (фон в тайлах — карта комнаты известна). Герой остаётся как есть.
Решить, как мумия и герой ведут себя при пересечении (герой поверх; мумия не портит героя).

**Вариант B — упрощённые перекрытия.** При пересечении объектов без попиксельного слияния `vop_*/vom_*`: последний рисуется
поверх прямоугольником (или по маске без учёта соседа). Оценить отдельно и вместе с A.

Для каждого варианта:
1. Цена шага: `tick_breakdown.js` (стресс и natural), кадров на шаг (`lo_align`/`beam_harness`-сценарии demo/stress/tour1–3),
   доля 2-кадровых шагов. Сравнивать с базой `3p` в том же окружении.
2. Мерцание и картинка: штатные метрики (`gt_eval`, `st_eval2`, right-half/rh, bad_px/gone) — до/после; снимки кадров
   (мумия на фоне, мумия у героя, мумия у верха, на лестнице) — `outputs/mummy-zx/*.png`.
3. Логика не меняется: `tools/verify/lo_align.js` — 6/6 equal; `snd_tempo` — зелёный.
4. Гейты `tools/verify/run_gates.sh`: давно красные `spr_resid_gate`, `knife_purity`, `bonus_ending_gate` — не новые; новых
   красных быть не должно (кроме тех, что проверяют именно старый вывод мумий — переписать с объяснением).
5. Память: свободно до romCeil (0x75A5) и в зоне данных запуска — до/после (сейчас запас десятки байт; новый путь может
   освободить код старого композита — посчитайте).

## Ограничения и ловушки
- Скорость и поведение логики — как у оригинала (Z80/MSX); менять только вывод.
- Модель луча в эмуляторе совпадает с MiSTer (проверено снимками, `beam-calib`), BEAMW не убирать без отдельного замера.
- Кадровый IRQ под DI не защёлкивается (mus-jitter): не держать DI дольше прежнего.
- Не путать «не тронуто стендами» со «свободно»; проверять окна ОЗУ по `ACCESS`-картам на нескольких сценах.
