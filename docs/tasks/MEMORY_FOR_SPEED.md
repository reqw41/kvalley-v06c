# Задача: найти память под предсдвиг мумий и кэш тайлов (KV1, ванильный Вектор)

## Контекст

Живая линия — ветка `3p` (после приёмки — с правками `flicker-kv2`, см. `outputs/flicker-kv2/REPORT.md`).
Память на нуле: до romCeil свободно ~24 Б, ОЗУ p3 — куски по десятки байт (одна свободная страница — слот 14).

Замер текущей сборки (`tools/verify/mz_prof_obj.js`, такты на игровой шаг; шаг demo ~107 тыс., 2,39 кадра):

| | demo | stress | tour1 |
|---|---|---|---|
| сдвиг и сборка кадра героя | 11 183 | 8 516 | 8 352 |
| сдвиг кадра мумий | 3 924 | 4 715 | 4 980 |

Две меры, которым не хватает только памяти:

1. **Предсдвиг мумий** при загрузке пирамиды: 3 кадра × 2 направления × 8 сдвигов × 48 Б = **2304 Б**
   (без нулевого сдвига 2016 Б). Ожидание: −3…−4 тыс. тактов на шаг (+3–4 % темпа). Таблица не меняется до
   смены пирамиды — замираний нет.
2. **Кэш тайлов для фона героя** (замер flicker-kv2: на пирамиду 25–29 разных ненулевых 8-байтных блоков по
   плоскостям, ~240 Б + таблица ID → блоки; код ~300 Б). Убирает сохранение фона героя, сдвиг фона в слоте и окно
   «герой стёрт, пока мумии XOR-ятся» (главный остаток мерцания рядом с мумией). Ожидание: −3…−5 % темпа.

Предсдвиг героя НЕ делать: 6,7 КБ и замирание при подборе ножа/кирки (набор кадров перезагружается).

## Что сделать

1. Опись (по образцу `tools/verify/fk_space.js`): все области образа и ОЗУ с размером и «горячее/холодное», крупные
   кандидаты: сжатые карты `res_maps.asm` (1590 Б, нужны только при загрузке), потоки звука (~1 КБ),
   `vec_sprdata.asm` (800 Б), графика меню/титула `res_ui_gfx.asm` (569 Б), холодный код (концовка, прокрутка,
   кирка), буфер save-under слотов 4/5 (освобождается при кэше тайлов). Для каждого — способ освободить (сжать,
   распаковывать по требованию, слить, держать в p3) и цена в тактах/поведении.
2. Итог описи — таблица «сколько можно освободить без потери поведения». Если ≥ 2,3 КБ — сделать предсдвиг мумий;
   если ещё ≥ 0,5 КБ — кэш тайлов для героя.
