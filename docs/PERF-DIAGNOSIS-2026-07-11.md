# KV Вектор-06Ц — диагностика производительности (2026-07-11)

**Цель:** дотянуть рекомпилированный KV до плавности оригинала MSX (полный кадр 50 Гц
без обрыва ISR посреди рендера и без флика).

**База:** HEAD `e614383` (ветка `plane-split-overwrite`), исходник `tools/kv_z80_to_8080.py`
(рекомпилятор Z80→i8080 + soft-VDP рантайм). Сборка:

```
python3 tools/kv_z80_to_8080.py msx/kvalley_src.asm /tmp/kvv.asm --target vector
tools/bin/sjasm -s /tmp/kvv.asm <rom> /tmp/kvv.lst /tmp/kvv.sym
```

Движок в ходе диагностики **НЕ менялся** (все пробные правки откачены).

---

## 1. Бюджет кадра — кадр насыщается

Инструмент: `tools/verify/frame_budget.js <rom>` (idle-метод: доля не-halt циклов = «работа»;
halt = opcode 0x76 крутится до прерывания).

| Состояние | avg работа | пик | что значит |
|---|---|---|---|
| стоя | ~96% | 100% | почти нет запаса |
| движение влево | ~89% | **100%** (total≈59888cy, idle=0) | **кадр упирается в потолок** |

Бюджет кадра ~59904 такта (3 МГц / 50 Гц). Пики 100% = ISR не успевает, рендер рвётся →
медленность и флик. Это и есть разрыв с MSX.

## 2. Хотспот — soft-VDP фона, НЕ спрайты

Инструмент: `tools/verify/pc_profile.js <rom> <sym>` (гистограмма циклов по меткам .sym).
Профиль при движении (200 кадров):

| Регион | % кадра | Что это |
|---|---|---|
| `vtd_scan` + `vtd_sn` | **20.4%** | линейный скан 256 name-клеток на каждый изменённый тайл |
| `vec_vram_write` + `setVDPWrite` | 8.4% | перехват VDP-записей |
| `dummyLoop` + `vcp_cells` | ~9% | слив грязных клеток (блит фона) |
| `vec_blit_tile` + `vec_fill_col` + `vw_name` | ~7% | компоновка тайлов фона |
| **спрайты** (`vec_xor_col`/`vxq*`) | **не в топ-30** | ← пивот на моно-спрайты сэкономит ≈0 |

**Спрайты — не бутылочное горлышко.** Задуманный пивот (моно-XOR-спрайты в отдельной плоскости)
не даёт скорости И невозможен: ни p2, ни p3 не свободны (заняты ~14K теней). Отменён.

## 3. Корень: скан пропагации мерцания сокровищ

- Игра мерцает **гем-тайлы `0x51, 0x52, 0x53, 0x5c` (в каждом из 3 банков)** каждые ~3 кадра,
  переписывая их **pattern/color**. На MSX железо VDP рендерит из таблиц построчно — смена
  паттерна тайла мгновенно и бесплатно перекрашивает все клетки с этим тайлом.
- Наш soft-VDP должен пропагировать это программно: `vec_td_mark` (~6/кадр) метит тайл грязным,
  `vec_compose` для каждого грязного тайла **сканирует все 256 name-клеток банка**, ища где тайл
  на экране (O(256) на тайл) → `vec_dirty_set` найденным клеткам → блит. Скан = 20% кадра.
- **Реверс-мап-кэш** (`vec_rmap` @0x7E5E, 12 слотов direct-map `(bank<<2)|(tile&3)`, 3 клетки/слот)
  должен ловить повторные марки одного тайла и отдавать клетки без скана. **Промах 100%:**
  1. гем-тайлы переполняют ёмкость 3 клетки/слот (>3 клеток → sentinel «не кэшировать»);
  2. name-таблица пишется **7.65/кадр** (мерцание свопает тайлы клеток), и КАЖДАЯ name-запись
     инвалидирует 2 слота rmap (`vw_name`, строки 879/884) → кэш вечно холодный.
- Замер кэша (корректный): `HIT=0 OVERFLOW=0 COLLIDE=1190 (100%)`, слоты держат мусор/0xFF.

## 4. План фикса (реализация ОТЛОЖЕНА по решению юзера — только замер)

**Структурное лечение — постоянный обратный индекс тайл→клетки:**
- Для каждого (bank, tile) — список экранных клеток, поддерживаемый инкрементально при
  name-записях (`vw_name` и так трогает rmap — там точка расширения).
- `vec_td_mark` идёт по списку клеток тайла за O(клеток), а не сканом O(256). `vec_compose`
  Phase-1 скан ИСЧЕЗАЕТ. Возврат ~20% бюджета.
- Реализация: массив `next[768]` (клетка→следующая в списке) + головы `head[3×256]` (тайл→
  первая клетка, 0xFF=пусто). ~1.5K. Память тесная (хвост 0x7E00-0x8000 забит; планы 2,3 под
  тени) — нужен аккуратный поиск места, ПОЭТАПНО с замером (крупные правки раскладки раньше
  роняли сборку — см. историю в памяти `project_kv_r3_on_recompiled`).
- Вторичная цель после индекса: перехват VDP-записей (`vec_vram_write`, 8%).

**Дешёвые низкорисковые правки (кандидаты, если индекс отложить):** реже `vec_setpal`
(палитра статична), меньше budget у `vec_compose`, дедуп повторных pattern-записей одного тайла
в кадре. Ожидаемый эффект — единицы %, не решает корень.

**Что НЕ поможет:** пивот на моно-спрайты (спрайты дёшевы); дедуп 3 банков (банки раздельны в
HEAD-базе, клетки каждого банка реально нужно обновлять).

## 5. Инструменты (постоянные, в `tools/verify/`)

- `frame_budget.js <rom> [holdSpace] [moveFrames] [warmup]` — бюджет кадра (idle-метод).
- `pc_profile.js <rom> <sym> [...]` — гистограмма циклов по регионам.

**Грабли инструментария (важно для будущих проб):** в `vector06js/i8080-js/i8080.js` регистры
`h,l,b,c,d,e,a` — это МЕТОДЫ (`cpu.h()`), НЕ свойства. Читать `cpu.regs[4]=H, [5]=L, [0]=B,
[1]=C, [2]=D, [3]=E, [7]=A`. `cpu.pc/sp/vcycles/last_opcode` — свойства. Файлы `.asm/.lst` в
latin-1 → `grep` только с `LC_ALL=C` или `-a` (иначе бинарный режим глушит совпадения).
Проверка визуала — только `tools/verify/honest_render.js` (дамп реального v06c.bmp).
