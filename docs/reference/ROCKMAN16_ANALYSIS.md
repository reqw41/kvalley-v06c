# Rockman 16 (Вектор-06Ц): разбор техники рендера

Разобрано 2026-07-30 запуском ROM в ядре vector06js + дизассемблированием.
ROM: ~/projects/vector06js/rockman16.rom, 21843 Б, вход JMP 0x0450. Клон Boulder Dash.

## 1. СКРОЛЛА КАК ТАКОГО НЕТ
Движок безусловно и непрерывно перерисовывает ВСЁ игровое поле из карты, по кругу,
независимо от того, скроллится экран или нет. «Скролл» = прибавление ±1 или ±33 к
указателю окна карты. **Стоимость самого скролла ≈ 50-100 тактов.**

```
0d5a: 2a 89 0b  LHLD 0B89    ; указатель окна карты
0d5d: 19        DAD D        ; += дельта   <-- ВЕСЬ СКРОЛЛ
0d5e: 22 89 0b  SHLD 0B89
```
Шаг: горизонтально 8 px, вертикально 16 px. Порт 0x03 (аппаратный vscroll) НЕ используется,
ISR его явно обнуляет (0x0D7C). Счётчик тайлов на проход всегда ровно 192 (16 колонок x 12 рядов).

## 2. СДВИГ НА 8 px ПО ГОРИЗОНТАЛИ БЕСПЛАТЕН
Тайл 16x16 пишется в ДВЕ соседние байт-колонки fb, а колонка — это старший байт адреса.
Сдвиг картинки на 8 px = начать сетку тайлов с другой (нечётной) колонки. **Ни одного такта
ротации.** Кромка (оставшиеся 8 px) рисуется 12 «половинными» вариантами тайлов.

## 3. КОМПИЛИРОВАННЫЕ ТАЙЛЫ ЧЕРЕЗ PUSH-ХАЙДЖЕК
Каждый тайл — процедура в ROM, пиксели вкомпилированы в операнды `LXI H`, запись через
`PUSH H` (2 байта = 2 растровые строки за одну инструкцию), SP наведён на видеопамять.
```
0f9e: 21 f0 0c  LXI H,0CF0   ; данные 2 строк
0fa1: e5        PUSH H       ; 16 тактов на 2 байта = 8 т/байт (ПОЛ ТЕХНИКИ)
...              8 push = 16 строк одной колонки одной плоскости
0fbc: 21 10 20  LXI H,2010 / DAD SP / SPHL   ; переход на следующую плоскость/колонку
```
Диспетчер 0x0BE6-0x0BFB (100-116 тактов): читает байт карты, `ANI 1E` (16 кодов),
`ADI фаза` (self-mod операнд = фаза анимации), патчит младший байт `LHLD`, `PCHL`.
Анимация тайлов БЕСПЛАТНА: в конце прохода фаза крутится по 4 банкам.
Библиотека: 69 процедур, 7787 Б = ~114 Б кода на тайл 16x16x2 плоскости (64 Б пикселей), x1.8.

## 4. СТОИМОСТЬ (замерено, кадр Вектора 59904 такта)
| величина | значение |
|---|---|
| тайл 16x16, 2 плоскости (64 байта) | 796-1108 тактов, типично **1056** |
| на байт видеопамяти | 12.4-17.3, типично **16.5** такта |
| «пол» техники (подряд PUSH без LXI) | **8 такта/байт** |
| полный проход экрана | 192 тайла = 12288 Б ≈ **203 000 такта ≈ 3.4 кадра** |
| фактический темп | 4 кадра/проход в покое, 6 когда «кипит» => 8-12 fps |
| разбивка кадра | тела тайлов 69.7%, диспетчер 11.5%, HLT 15.1%, ЛОГИКА 3.8% |

## 5. ДВОЙНАЯ БУФЕРИЗАЦИЯ = ПЕРЕКЛЮЧЕНИЕ ПАЛИТРЫ (цена — 4 цвета)
- страница A = плоскости 0x8000 + 0xA000, страница B = 0xC000 + 0xE000
- флип рисования: один XOR в ISR (`LDA 0B87 / XRI 40 / STA 0B87`)
- флип экрана: перезагрузка палитры (0x0DA1-0x0DE4), 16 записей, но всего **4 цвета**,
  разложенных так, что две плоскости становятся «безразличными»:
  кадр N:   цвет = f(биты 0,1) -> видна страница B
  кадр N+4: цвет = f(биты 2,3) -> видна страница A
- игровое поле = 2 битовые плоскости, 4 цвета (0x002020, 0x80a0a0, 0xc08000, 0xc0e0e0)
- статичное табло сверху записано во ВСЕ 4 плоскости (p0==p2 && p1==p3) — видно при любой палитре
**ГОНОК С ЛУЧОМ НЕТ ПО ПОСТРОЕНИЮ**: видимая страница при рисовании не трогается.
Флип строго в VBlank. Окно для прерывания — одна инструкция между полосами:
`LXI SP,real / EI / <1 инстр> / DI / SPHL` (0x0C3C-0x0C48).

## 6. СПРАЙТОВОГО ДВИЖКА НЕТ ВООБЩЕ
Герой, камни, алмазы — клетки карты; логика правит карту, а не экран. Отсюда 3.8% CPU на логику.

# ЧТО ПРИМЕНИМО К KING'S VALLEY (по убыванию выигрыша)
1. **PUSH вместо POP в блиттере — в 2-2.5 раза.** Наш vbt_row: `POP DE` + 2x`LD (HL),r` +
   2x`DEC L` ≈ 20 такта/байт. У них `PUSH H` = 8 такта/байт, и данные не читаются из памяти
   вовсе (они в коде). Требует компиляции паттернов.
2. **Укрупнить тайл до 16x16** — размазать фиксированные ~230 такта диспетчера на 64 байта
   вместо 24. Прикидки для KV: 8x8x3пл ~22.8 т/байт (комната ≈6.4 кадра); 16x16x3пл
   ~16.8 т/байт (≈4.7 кадра); 16x16x2пл ~1056 такта (≈3.1 кадра).
3. **Сдвиг на кратное 8 px ротации НЕ ТРЕБУЕТ.** Наш шаг скролла = 4 знакоместа = 32 px =
   ровно 4 байт-колонки. Если сейчас на шаге что-то крутится — чистая потеря.
4. **Непрерывный ролл-рендер вместо «перерисовки по событию».** У них нет режима «сейчас
   скролл». Для KV: ScrollPantalla (GS=9) исчезает как дорогой режим, 8 шагов транзита
   становятся 8 обычными кадрами с другим указателем окна карты.
5. **Флип страниц через палитру, если согласиться на 4 цвета.** Полное отсутствие мерцания
   и разрывов бесплатно (флип ≈600-900 такта). Итог: комната ≈3.1 кадра, транзит 8 шагов
   ≈25 кадров ≈0.5 с, БЕЗ save-under, БЕЗ dirty-очереди, без гонок с ISR.
6. Мелочи: окно прерывания в одну инструкцию между полосами; фаза анимации как смещение
   базы таблицы (анимированные тайлы бесплатны); карта колоночная, «вниз по экрану» = DCX B.

# НЕ ПРИМЕНИМО
- **Аппаратный vscroll (порт 0x03) для ФЛИПА** — две страницы по 176-192 строки в 256 строк
  fb не влезают (нужно ≤128 строк на страницу). Для вертикального скролла поля годится.
- **8 цветов + палитровый флип взаимоисключающи**: флип требует по 2 свободные плоскости на
  страницу. Либо 8 цветов и однобуферный рендер (гонка луча + save-under, как сейчас), либо
  4 цвета и чистая двойная буферизация. Третьего на Векторе нет.
- **Отказ от спрайтового движка** (объекты как клетки карты) — для KV невозможно: герой,
  мумии, нож двигаются попиксельно.
- Их скролл НЕ гладкий: 8 px по горизонтали, 16 по вертикали, при 8-12 fps.
- **Расход ROM на компилированные тайлы**: у них работает потому, что кодов тайлов всего 16
  (маска ANI 0x1E) x 4 фазы = 69 процедур = 7.8 КБ. Для KV надо считать число различимых
  образов; при 3 плоскостях ROM может не вытянуть — компилировать только горячие тайлы.

# ЕСЛИ ДЕЛАТЬ ОДИН ШАГ
Скомпилировать 16x16 метатайлы фона в PUSH-процедуры (p0/p1) и заменить путь
`drawRoom -> getTileFromID -> vec_text_blit -> vec_blit_tile -> vbt_row -> vec_su_fixup`
на диспетчер из ~12 инструкций + PCHL. Даже без перехода на 4 цвета это снимает пролог на
тайл, su_fixup и чтение паттерна: ожидаемо 16.8 вместо ~40+ такта на байт.

ОГОВОРКА АВТОРА РАЗБОРА: замерить «до» на нашем ROM не удалось (headless не доводит до GS=9),
поэтому цифры для KV аналитические — перезамерить своим гейтом (scratchpad/scroll_probe.js).
